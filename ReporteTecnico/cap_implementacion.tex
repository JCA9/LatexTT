\subsubsection{Comunicación con el backend}

Toda la comunicación entre la aplicación móvil y el backend se realiza
mediante \textbf{API REST} sobre HTTPS. El cliente HTTP centralizado
\campo{ApiService} (singleton) gestiona:

\begin{itemize}
  \item Inyección automática del token JWT en el header
        \campo{Authorization}.
  \item Decodificación de respuestas en formato \campo{\{success, data\}}.
  \item Timeouts configurables: 30 segundos para peticiones normales,
        60 segundos para el endpoint OCR.
  \item Manejo de errores HTTP (400, 401, 403, 404, 409, 500).
  \item Subida de imágenes mediante \campo{multipart/form-data}.
\end{itemize}

La URL base del backend es:
\endpoint{https://documents.digitaltax-analytics.com/finara/api}

\subsubsection{Manejo de estado}

La aplicación utiliza el patrón \textbf{StatefulWidget + setState} de
Flutter sin gestores de estado globales. Cada pantalla administra su
propio estado local. La capa de servicios (\campo{*Service}) actúa como
intermediaria entre la UI y el backend, abstrayendo la lógica HTTP.

\begin{notabox}
  No se utilizan paquetes como Provider, Riverpod o Bloc. El estado es
  local a cada widget. La comunicación entre pantallas se realiza mediante
  valores de retorno en \campo{Navigator.push} (\campo{result == true})
  que disparan recargas en la pantalla padre.
\end{notabox}

\subsection{Módulo de escaneo de tickets (OCR)}
% ──────────────────────────────────────────────────────────────

\subsubsection{Descripción general}

El módulo de escaneo es el componente más diferenciador de FINARA. Permite
al usuario fotografiar uno o varios tickets de compra y extraer
automáticamente los productos, precios, tienda y total mediante un pipeline
de OCR de múltiples etapas. El resultado alimenta directamente el registro
de gastos y el control de presupuestos.

\subsubsection*{Flujo completo de operación}

\begin{enumerate}
  \item \textbf{Captura} (\campo{ScanTicketScreen}): El usuario activa la
    cámara trasera y captura entre 1 y 5 fotografías del ticket.
  \item \textbf{Previsualización} (\campo{ScanPreviewScreen}): Carrusel de
    imágenes con opción de eliminar, añadir más fotos o confirmar.
  \item \textbf{Procesamiento} (\campo{ScanProcessingScreen}): Las imágenes
    se suben al backend vía \campo{multipart/form-data}. El backend invoca
    el script Python OCR y devuelve el JSON estructurado.
  \item \textbf{Resultado} (\campo{ScanResultScreen}): El usuario revisa,
    edita o elimina los productos detectados antes de guardar el gasto.
\end{enumerate}

\subsubsection{Pantallas del módulo}

\subsubsection*{ScanTicketScreen — Captura de imágenes}

Utiliza el plugin \campo{camera} para inicializar la cámara trasera con

  \item Regresar a la cámara para añadir más fotos (respeta el límite

  \item Confirmar el lote de imágenes y pasar al procesamiento.

\subsubsection*{ScanProcessingScreen — Ejecución OCR}

Es la pantalla de espera durante el procesamiento. Muestra 6 pasos

\begin{enumerate}
  \item Preparando imágenes
  \item Subiendo al servidor
  \item Ejecutando OCR
  \item Extrayendo texto
  \item Identificando productos
  \item Calculando totales
\end{enumerate}

La petición al backend se realiza mediante \campo{TicketsService.scanTicket()}:

  \item Cambiar la fecha de la compra con un \campo{DatePicker}.
  \item Ver la confianza OCR del escaneo (indicador verde/naranja).

\subsubsection{Pipeline OCR en el backend}

El script \archivo{ocr/LecturaTickets\_v2.py} implementa un pipeline de
6 etapas ejecutado como subproceso de Node.js:

\begin{enumerate}
  \item \textbf{Preprocesamiento} (OpenCV): upscaling a mínimo 1\,200 px,
        corrección de iluminación, deskew, binarización adaptativa
        gaussiana, denoising y sharpening.
  \item \textbf{OCR con Tesseract}: modo LSTM (\campo{oem 3}), bloque de
        texto (\campo{psm 6}), idiomas \campo{spa+eng}. Retorna texto y
        confianza promedio por palabra.
  \item \textbf{Evaluación de calidad}: dos compuertas independientes.
  \item \textbf{Respaldo Vision + Claude} (si aplica).
  \item \textbf{Parsing por regex}: extracción de productos, total y fecha.
  \item \textbf{Categorización}: pipeline de 3 pasos por producto.
\end{enumerate}

\subsubsection*{Respaldo con Google Cloud Vision + Claude}

Cuando se activa cualquier compuerta, la función
\campo{\_enhance\_extraction()}:

\begin{enumerate}
  \item Codifica la imagen en base64 y la envía a la API de Google Cloud
        Vision
  \item Si se obtiene texto, lo envía a Claude Haiku con un prompt que
        estructura el ticket en JSON
        (\campo{store\_name, date, total, products}).
  \item El JSON enriquecido se deserializa al formato interno del pipeline.
  \item La confianza se establece en 0.95 si Vision fue exitoso.
\end{enumerate}

Si las claves API no están disponibles o cualquier paso falla, la función
retorna el texto original de Tesseract sin lanzar excepción.

\subsubsection*{Categorización automática de productos}

Cada producto detectado pasa por un pipeline de 3 pasos:

\begin{enumerate}
  \item \textbf{categorias.json}: comparación del nombre del producto
        contra palabras clave organizadas por categoría. Match por
        substring exacto o similitud \campo{SequenceMatcher}
        $\geq 0.75$.
  \item \textbf{Historial del usuario}: si el Paso~1 no encontró
        categoría, se consultan los productos previos del mismo usuario
        en \campo{Productos\_Tickets}. Match por substring o similitud
        $\geq 0.70$.
  \item \textbf{Fallback}: si ninguno encontró coincidencia, el producto
        se asigna a la categoría ``Otros'' con
        \campo{id\_categoria = null}.
\end{enumerate}

\begin{lstlisting}[style=python,
    caption={Pipeline de categorización de productos — Paso 1}]
# Pipeline de categorizacion -- Paso 1 (categorias.json)
def _classify_by_json(name, categories):
    name_up = name.upper()
    for cat, keywords in categories.items():
        if cat == "OTROS": continue
        for kw in keywords:
            if kw.upper() in name_up:
                return cat          # Coincidencia exacta por substring
            if SequenceMatcher(None, name_up, kw.upper()).ratio() >= 0.75:
                return cat          # Coincidencia fuzzy
    return None                     # Sin coincidencia
\end{lstlisting}

\subsubsection*{Métrica de confianza del ticket}

La función \campo{calculate\_confidence()} combina la confianza técnica
de Tesseract con señales estructurales del parsing. El valor final se
normaliza al rango $[0.0,\ 1.0]$ con \campo{max(0, min(score, 1))}.

\subsubsection{Consideraciones técnicas}

\begin{itemize}
  \item \textbf{Idempotencia}: el backend genera un hash SHA-256 de las
        imágenes para evitar procesar el mismo ticket dos veces (error
        409 en duplicados).
  \item \textbf{Limpieza}: los archivos temporales de imagen se eliminan
        del servidor tras procesar el ticket.
  \item \textbf{Transacciones DB}: el ticket y sus productos se insertan
        en una transacción con \campo{rollback} ante cualquier falla.
  \item \textbf{Manejo de errores en Flutter}: si el OCR lanza excepción,
        la pantalla de procesamiento permite reintentar sin necesidad de
        fotografiar nuevamente el ticket.
\end{itemize}

\subsection{Módulo de categorías}
% ──────────────────────────────────────────────────────────────

\subsubsection{Descripción general}

El módulo de categorías provee la estructura de clasificación que sustenta
todos los demás módulos. Cada gasto, producto de ticket, presupuesto e
ingreso queda asociado a una categoría del usuario. El sistema distingue
dos tipos: \textbf{predefinidas} (creadas durante el onboarding) y
\textbf{personalizadas} (creadas libremente por el usuario).

Las categorías predefinidas por defecto son: Alimentos, Entretenimiento,
Transporte, Ahorro y Ropa.

\subsubsection{Flujo funcional}

\begin{enumerate}
  \item El usuario navega a la pantalla de Categorías desde el módulo de
        Presupuestos o desde el menú de configuración.
  \item Ve el listado separado en dos secciones.
  \item Para crear: presiona el botón ``+'' y completa el formulario.
  \item El servicio llama al endpoint POST y recarga la lista en caso de
        éxito.
  \item La nueva categoría queda disponible inmediatamente para asignar
        en presupuestos, gastos y productos de tickets.
\end{enumerate}

\subsubsection{Consideraciones técnicas}

\begin{itemize}
  \item Las categorías predefinidas no pueden eliminarse desde el
        frontend (el botón de edición no aparece en la sección
        predefinidas).
  \item En caso de error al cargar, se muestra un estado de error con
        botón de reintentar en lugar de pantalla vacía.
  \item El servicio retorna lista vacía (no lanza excepción) ante
        cualquier error HTTP, para no bloquear formularios que dependan
        de las categorías.
\end{itemize}

\subsection{Módulo de presupuestos}
% ──────────────────────────────────────────────────────────────

\subsubsection{Descripción general}

El módulo de presupuestos permite al usuario asignar un límite de gasto
mensual por categoría. El sistema calcula automáticamente cuánto se ha
gastado en cada categoría durante el mes en curso y emite alertas cuando
el presupuesto está cerca de agotarse o ha sido superado.

Cada presupuesto cubre el rango de fechas del mes calendario actual
(del día~1 al último día del mes), calculado automáticamente tanto en el
frontend como en el backend.

\subsubsection{Modelo de datos}

\begin{lstlisting}[style=dart,
    caption={Modelo de datos Budget en Flutter}]
class Budget {
  final int      id;
  final int      idCategoria;
  final double   montoAsignado;
  final double   montoUtilizado;   // Actualizado por el backend
  final String   periodo;          // 'mensual' (fijo)
  final DateTime fechaInicio;
  final DateTime fechaFin;
  final bool     activo;

  // Propiedades calculadas
  double get porcentajeUtilizado =>
      (montoUtilizado / montoAsignado * 100).clamp(0, double.infinity);

  double get montoDisponible =>
      (montoAsignado - montoUtilizado).clamp(0, double.infinity);
}
\end{lstlisting}

\subsubsection{Pantallas}

\subsubsection*{BudgetsScreen — Panel de presupuestos}

La pantalla principal del módulo presenta:

\begin{itemize}
  \item \textbf{Tarjeta resumen global}: presupuesto total asignado,
        total gastado y porcentaje de uso del mes.
  \item \textbf{Barra de progreso global}: cambia a rojo cuando el uso
        supera el 90\%.
  \item \textbf{Tarjetas por presupuesto}: icono de categoría, nombre,
        barra de progreso individual, monto gastado vs.\ asignado,
        porcentaje y botón de edición.
  \item \textbf{Estado vacío}: con ícono y llamada a la acción para
        crear el primer presupuesto.
\end{itemize}

\begin{lstlisting}[style=dart,
    caption={Cálculo de totales en BudgetsScreen}]
// Calculo de totales en la pantalla
double get _totalBudget =>
    _budgets.fold(0, (s, b) => s + b.montoAsignado);

double get _totalSpent =>
    _budgets.fold(0, (s, b) => s + b.montoUtilizado);

double get _percentageUsed =>
    _totalBudget > 0 ? (_totalSpent / _totalBudget * 100) : 0;
\end{lstlisting}

\subsection{Módulo de deudas}
% ──────────────────────────────────────────────────────────────

\subsubsection{Descripción general}

El módulo de deudas gestiona créditos e instrumentos de deuda con soporte
para la \textbf{fórmula de amortización francesa}. Permite registrar el
capital inicial, la tasa de interés anual, el plazo en meses y la fecha
del próximo pago. El backend calcula el pago mensual, la tasa mensual
equivalente y el saldo insoluto tras cada abono. El usuario puede realizar
pagos ordinarios y abonos extraordinarios a capital.

\subsubsection{Modelo de datos}

\begin{lstlisting}[style=dart,
    caption={Modelo de datos Debt en Flutter}]
class Debt {
  final int      id;
  final String   nombreDeuda;
  final double   capitalInicial;
  final double   tasaAnual;
  final double   tasaMensual;      // tasaAnual / 12
  final double   saldoInsoluto;    // Saldo pendiente post-pagos
  final double   pagoMensual;      // Calculado por backend
  final double   montoPagado;      // Acumulado de pagos
  final int      duracionMeses;
  final DateTime fechaSiguientePago;
  final bool     activa;

  // Propiedades calculadas en cliente
  double get porcentajePagado  => montoPagado / capitalInicial * 100;
  double get montoPendiente    => (capitalInicial - montoPagado)
                                    .clamp(0, double.infinity);
  double get interesTotal      => (pagoMensual * duracionMeses)
                                    - capitalInicial;
  bool   get tieneInteres      => tasaAnual > 0;
  int    get diasHastaPago     => fechaSiguientePago
                                    .difference(DateTime.now()).inDays;
}
\end{lstlisting}

\subsubsection{Fórmula de amortización francesa}

El pago mensual se calcula usando la fórmula estándar de cuota fija:

\[
  M = C \cdot \frac{r}{1 - (1 + r)^{-n}}
\]

donde $C$ es el capital inicial, $r$ es la tasa mensual
($r = \text{tasa\_anual} / 1200$) y $n$ es el número de mensualidades.
El frontend calcula esta fórmula en tiempo real para mostrar una vista
previa antes de guardar la deuda:

\begin{lstlisting}[style=dart,
    caption={Cálculo del pago mensual con amortización francesa}]
// Calculo del pago mensual con amortizacion francesa
double get _tasaMensual => _tasaAnual / 1200;

double get _pagoMensual {
  if (_capital <= 0 || _meses <= 0) return 0;
  if (_tasaMensual == 0) return _capital / _meses;
  final r = _tasaMensual;
  final n = _meses;
  return _capital * r / (1 - pow(1 + r, -n));
}
\end{lstlisting}

Para deudas sin interés (\campo{tasaAnual == 0}), el cálculo simplifica
a la división directa del capital entre el número de meses.

        \campo{DateTime.difference} para evitar tráfico innecesario.

\section{Backend}

El backend de FINARA constituye el núcleo lógico del sistema. Es el

\subsubsection{Arquitectura en capas}

El backend implementa una arquitectura de \textbf{tres capas} con una
capa adicional de servicios especializados:

\begin{enumerate}
  \item \textbf{Capa de presentación (Routes):} Los doce routers
    registrados en \archivo{app.js} reciben las solicitudes HTTP,
    aplican middleware de autenticación y de validación, y delegan al
    controlador correspondiente.

  \item \textbf{Capa de aplicación (Controllers):} Cada controlador
    contiene la lógica de negocio de su módulo. Consulta o modifica la
    base de datos mediante el pool de conexiones y devuelve respuestas
    estandarizadas.

  \item \textbf{Capa de servicios especializados (Services):} Para
    operaciones complejas —procesamiento OCR, generación de
    recomendaciones con IA o rollover de datos periódicos— los
    controladores delegan en servicios dedicados que encapsulan dicha
    lógica.

  \item \textbf{Capa de datos (Database):} Un pool de conexiones
    centralizado en \archivo{config/database.js} gestiona el acceso a
    MySQL. Todas las consultas usan sentencias preparadas con
    parámetros para prevenir inyección SQL.
\end{enumerate}

\subsubsection{Configuración de Express y cadena de middleware}

\subsection{Autenticación y seguridad}
% ──────────────────────────────────────────────────────────────

\subsubsection{Estrategia JWT}

La autenticación se basa en \textbf{JSON Web Tokens} sin estado del
lado del servidor. Al iniciar sesión exitosamente, el backend firma un
token con el algoritmo \texttt{HS256} que contiene el
\campo{userId} y el \campo{email} del usuario. El token es
enviado al cliente, quien lo incluye en cada solicitud
subsiguiente mediante el encabezado:

\begin{lstlisting}[style=codigobase, language={}]
Authorization: Bearer <token>
\end{lstlisting}

El tiempo de vigencia predeterminado es de siete días
(\campo{JWT\_EXPIRES\_IN=7d}). Una vez expirado, el cliente debe
autenticarse de nuevo.

\subsubsection{Middleware de autenticación}

El middleware en \archivo{middleware/auth.js} protege todos los
endpoints excepto los de autenticación. Su lógica es la siguiente:

\begin{enumerate}
  \item Extrae el token del encabezado \campo{Authorization}.
  \item Si no existe o no comienza con \texttt{Bearer}, responde con
    \texttt{401 Unauthorized}.
  \item Verifica la firma con \campo{JWT\_SECRET} usando
    \campo{jwt.verify()}.
  \item Ante \campo{TokenExpiredError} responde con el mensaje
    ``Token expirado''; ante cualquier otro error, ``Token inválido''.
  \item Si la verificación es exitosa, adjunta el objeto
    \lstinline[style=codigobase]|req.user = { userId, email }| y
    llama a \campo{next()}.
\end{enumerate}

Gracias a este modelo, \textbf{todos los endpoints de datos filtran
automáticamente por} \campo{req.user.userId}, garantizando el
aislamiento completo entre cuentas de usuario sin necesidad de un
sistema de roles.

\subsubsection{Seguridad adicional}

\begin{itemize}
  \item \textbf{Hashing de contraseñas:} Se utiliza \texttt{bcrypt} con
    factor de costo 12. El hash resultante se almacena en la columna
    \campo{password\_hash} y nunca se expone en ningún endpoint.
  \item \textbf{Limitación de tasas:} \texttt{express-rate-limit}
    restringe el número de peticiones por dirección IP, mitigando
    ataques de denegación de servicio y de fuerza bruta contra el
    endpoint de login.
  \item \textbf{Validación de entrada:} Todos los endpoints definen
    un arreglo de validadores de \texttt{express-validator} que se
    ejecutan antes del controlador. Si alguna validación falla, el
    middleware \archivo{middleware/validator.js} interrumpe la cadena
    y responde con \texttt{400 Bad Request} y el mensaje de error
    específico.
  \item \textbf{Mensajes de error en producción:} El manejador de
    errores global comprueba \campo{NODE\_ENV}; si es
    \texttt{production}, el mensaje de excepción interno no se incluye
    en la respuesta al cliente.
\end{itemize}

\subsection{Módulos de la API REST}
% ──────────────────────────────────────────────────────────────

\subsubsection{Convenciones de respuesta}

El backend establece un formato de respuesta uniforme en el módulo
\archivo{utils/helpers.js}. Las respuestas exitosas adoptan la
estructura:

\begin{lstlisting}[style=codigobase, language={}]

\begin{lstlisting}[style=codigobase, language={}]

Los códigos HTTP utilizados son los estándares: \texttt{200 OK},

\texttt{410 Gone} para funcionalidades eliminadas.

\subsubsection{Módulo de autenticación (\texttt{/api/auth})}

Gestiona el registro, inicio y cierre de sesión, verificación de token

automáticamente dos operaciones en la misma transacción: la creación del
registro en \texttt{Usuarios} y la creación de las cinco categorías de

\subsubsection{Módulo de ingresos (\texttt{/api/incomes})}

Administra los registros de ingreso del usuario. Los ingresos pueden
ser de tipo único o recurrente. El endpoint
\endpoint{POST /recurrent-upsert} implementa la semántica de
``crear o actualizar'': si ya existe un ingreso recurrente con el
mismo nombre para el usuario, actualiza su monto; en caso contrario,
crea uno nuevo. El endpoint \endpoint{GET /total} acepta los
parámetros de consulta \campo{month} y \campo{year} para retornar
el acumulado de ingresos del período especificado.

\subsubsection{Módulo de gastos (\texttt{/api/expenses})}

Registra los egresos del usuario. Soporta la creación de un gasto
simple con \endpoint{POST /} o de un gasto con múltiples productos
asociados con \endpoint{POST /with-products}, operación que inserta
el gasto y sus productos en una sola transacción. El endpoint
\endpoint{GET /recent} retorna los últimos gastos del usuario
incluyendo siempre el nombre de la categoría mediante un
\texttt{JOIN} con \texttt{Categorias}. Las consultas de listado
aceptan filtros opcionales por mes y año.

\subsubsection{Módulo de presupuestos (\texttt{/api/budgets})}

Gestiona los presupuestos mensuales por categoría. Al crear un
presupuesto con \endpoint{POST /}, el controlador calcula
automáticamente las fechas de inicio y fin del mes especificado
y verifica que no exista ya un presupuesto activo para la misma
categoría en ese período. El campo \campo{monto\_utilizado} se
actualiza dinámicamente cada vez que se registra o modifica un gasto
asociado a dicha categoría.

El endpoint \endpoint{POST /rollover} permite copiar los
presupuestos de un mes origen a un mes destino sin duplicar registros
existentes, funcionalidad que también se invoca automáticamente por el
servicio de rollover mensual.

\subsubsection{Módulo de tickets y OCR (\texttt{/api/tickets})}

Este es el módulo de mayor complejidad del backend. Expone tres
variantes de escaneo OCR y la gestión completa del ciclo de vida de
un ticket.

\begin{table}[H]
  \centering
  \caption{Endpoints de escaneo del módulo de tickets}
  \label{tab:endpoints-tickets-ocr}
  \begin{tabular}{p{1.2cm} p{4.2cm} p{8.1cm}}
    \toprule
    \textbf{Método} & \textbf{Ruta} & \textbf{Descripción} \\
    \midrule
    POST & \endpoint{/scan} & Recibe hasta cinco imágenes por
      \texttt{multipart/form-data}. Invoca el pipeline OCR local
      (Python + Tesseract) y, si la confianza es insuficiente,
      escala al servicio web (Vision + Claude). \\
    POST & \endpoint{/scan-web} & Variante para la plataforma web:
      acepta una imagen o PDF y la procesa directamente mediante
      el servicio de visión artificial externo. \\
    POST & \endpoint{/scan-web-text} & Recibe texto plano previamente
      extraído y lo estructura en JSON de productos mediante
      Claude Haiku. \\
    \bottomrule
  \end{tabular}
\end{table}

Para garantizar la idempotencia de las solicitudes de escaneo —y
evitar la creación de tickets duplicados ante reintentos de red— el
módulo implementa dos mecanismos complementarios:

\begin{itemize}
  \item \textbf{Hash de archivo:} Se calcula el hash SHA-256 de cada
    imagen. Si ya existe un ticket con ese hash en la base de datos,
    se retorna el ticket existente con el campo
    \campo{duplicate: true} en lugar de crear uno nuevo.
  \item \textbf{Llave de idempotencia:} El cliente puede enviar el
    encabezado \campo{x-idempotency-key} con un UUID generado por él.
    El backend almacena la llave en las notas del ticket y la
    comprueba antes de procesar.
\end{itemize}

El módulo también implementa un algoritmo de \textbf{sugerencia de
categorías} basado en similitud léxica. La función
\campo{scoreNameSimilarity()} tokeniza el nombre del producto y
lo compara con el historial de compras previas del usuario,
asignando pesos a coincidencias de prefijo y parciales. Si el
puntaje supera el umbral de 0.40, se asigna la categoría con
mayor frecuencia histórica; en caso contrario, se aplica un
clasificador por palabras clave definido en
\archivo{categorias.json}.

\subsubsection{Módulo de deudas (\texttt{/api/debts})}

Administra el ciclo de vida de las deudas del usuario con soporte
para \textbf{amortización francesa} (cuota fija mensual). Al crear
una deuda, el controlador calcula el pago mensual mediante la fórmula:

\begin{equation}
  M = C \cdot \frac{r}{1 - (1 + r)^{-n}}
  \label{eq:amort-francesa}
\end{equation}

donde $C$ es el capital inicial, $r$ es la tasa mensual y $n$ es la
duración en meses. Si la tasa es cero, la cuota se calcula como
$M = C / n$.

El endpoint \endpoint{GET /:id/amortization} genera el cronograma
completo de pagos, calculando para cada período el desglose entre
intereses y abono a capital con base en el saldo insoluto vigente.
Adicionalmente, el endpoint \endpoint{POST /:id/capital-payment}
permite registrar abonos extraordinarios que reducen el saldo insoluto
y recalculan el número de pagos restantes.

\subsubsection{Módulo de dashboard (\texttt{/api/dashboard})}

Provee los datos consolidados para la vista de resumen financiero. El
endpoint \endpoint{GET /summary} acepta los parámetros \campo{month}
y \campo{year} y retorna en una sola respuesta: totales de ingresos
y gastos, balance, estado de presupuestos (total asignado, total
utilizado, cantidad en alerta) y estado de deudas (deuda pendiente
total, pago mensual acumulado). Tras construir el resumen, el
controlador invoca \campo{checkBudgetAlerts()} y
\campo{checkDebtAlerts()} para generar de forma proactiva cualquier
alerta que aplique al período consultado.

\subsubsection{Módulo de alertas (\texttt{/api/alerts})}

Gestiona el centro de notificaciones del usuario. Las alertas son
generadas automáticamente por tres fuentes distintas:

\begin{enumerate}
  \item \textbf{Superación de presupuesto:} \campo{checkBudgetAlerts()}
    crea una alerta cuando el gasto de una categoría alcanza el 90\%
    del presupuesto asignado.
  \item \textbf{Vencimiento de deuda:} \campo{checkDebtAlerts()} crea
    una alerta cuando la siguiente fecha de pago de una deuda activa
    está a tres días o menos.
  \item \textbf{Recordatorio diario:} El cron job de recordatorios
    crea una alerta de gestión cada día a las 12:00 para usuarios que
    tengan activada esta preferencia.
\end{enumerate}

El endpoint \endpoint{PUT /mark-all-read} marca todas las alertas
no leídas del usuario como leídas en una sola operación.

\subsubsection{Módulo de recomendaciones (\texttt{/api/recommendations})}

Retorna recomendaciones financieras personalizadas para el período
indicado. La respuesta contiene cuatro secciones: un resumen textual,
una lista de riesgos identificados, recomendaciones accionables y
acciones sugeridas priorizadas. La generación sigue el pipeline
descrito en la sección \ref{sec:srv-recomendaciones}.

\subsection{Servicios especializados}
% ──────────────────────────────────────────────────────────────

\subsubsection{Servicio OCR local (\texttt{ocrService.js})}

Este servicio actúa como puente entre el controlador de tickets y el
script Python \archivo{ocr/LecturaTickets\_v2.py}. Recibe la ruta de
la imagen en disco y ejecuta el script como subproceso mediante
\campo{child\_process.spawn()}, pasando la ruta y el identificador
del usuario como argumentos. El proceso tiene un timeout configurable
(variable \campo{OCR\_TIMEOUT}) para evitar bloqueos ante imágenes
problemáticas.

El script Python implementa el mismo pipeline de seis etapas descrito
en la sección de la aplicación móvil: preprocesamiento con OpenCV,
extracción con Tesseract, evaluación de confianza y, si las dos
compuertas de calidad no se superan, señalización al servicio web
como respaldo.

\subsubsection{Servicio OCR web (\texttt{ocrWebService.js})}

\label{sec:srv-ocr-web}

Este servicio maneja los casos en que el OCR local no es suficiente o
cuando el cliente web envía directamente una imagen o PDF. Su flujo es:

\begin{enumerate}
  \item Codifica la imagen en base64 y la envía a la API de
    \textbf{Google Cloud Vision} para obtener el texto completo del
    documento.
  \item El texto extraído se envía a \textbf{Claude Haiku}
    (\campo{claude-haiku-4-5-20251001}) con un prompt estructurado que
    solicita la conversión del texto en bruto a un JSON con los campos:
    \campo{nombre\_tienda}, \campo{fecha}, \campo{total} y
    \campo{productos[]}.
  \item El JSON retornado por el modelo se valida, se persiste en la
    base de datos y se retorna al cliente con el mismo formato que el
    OCR local.
\end{enumerate}

\begin{notabox}[Modelo de lenguaje utilizado]
  El servicio utiliza \textbf{Claude Haiku} como modelo de
  estructuración, elegido por su velocidad de respuesta (~2 s) y
  costo reducido respecto a modelos mayores, dado que la tarea
  se limita a transformación de texto a JSON sin razonamiento
  complejo.
\end{notabox}

\subsubsection{Servicio de recomendaciones (\texttt{recommendationsService.js})}

\label{sec:srv-recomendaciones}

Para generar recomendaciones financieras personalizadas se sigue un
pipeline con caché de quince días:

\begin{enumerate}
  \item \textbf{Consulta de caché:} Se verifica si existe un registro
    vigente en \texttt{Recomendaciones\_Cache} para el usuario y
    período solicitados.
  \item \textbf{Recopilación de contexto:} Si no hay caché, el servicio
    consulta en paralelo: ingresos, gastos por categoría, estado de
    presupuestos y deudas activas del período.
  \item \textbf{Llamada a la IA:} Con el contexto financiero
    recopilado, construye un prompt y llama a Claude Haiku
    solicitando la estructura de respuesta con riesgos,
    recomendaciones y acciones priorizadas.
  \item \textbf{Almacenamiento en caché:} La respuesta del modelo se
    serializa como JSON y se guarda en \texttt{Recomendaciones\_Cache}
    con una fecha de expiración de quince días. Las llamadas
    subsiguientes al mismo período retornan el resultado cacheado
    instantáneamente.
  \item \textbf{Fallback automático:} Si la llamada a la IA falla por
    cualquier motivo (tiempo de espera agotado, error de API, cuota
    excedida), el servicio retorna un conjunto de recomendaciones
    predeterminadas basadas en reglas simples calculadas localmente.
\end{enumerate}

\subsubsection{Servicio de rollover (\texttt{budgetRolloverService.js},
  \texttt{incomeRolloverService.js})}

Estos servicios implementan la lógica de \textbf{traspaso automático}
de presupuestos e ingresos recurrentes de un mes al siguiente. El
servicio de presupuestos copia los registros activos del mes origen al
mes destino, omitiendo aquellos para los que ya exista un presupuesto
en el mes destino. El servicio de ingresos hace lo propio con los
ingresos marcados como recurrentes, creando nuevas entradas en el
período destino con los mismos montos.

Ambos servicios exponen tanto una función para un usuario individual
—utilizada cuando el propio usuario solicita un rollover manual— como
una función que itera sobre todos los usuarios del sistema —invocada
por el cron job mensual.
